# Measured accuracy, and where it actually stands

Numbers here are measured by the test suite against the synthetic fixtures in
`tests/fixtures/`, regenerated by `tools/make_fixtures.py`. They are honest
about a gap, so read the caveat before trusting them.

## The caveat that matters

**This project has never seen a real RS3 screenshot.** It was built in a cloud
environment whose network policy blocks `runescape.wiki` and
`secure.runescape.com`, so there were no real item icons, no real bank captures
and no live GE prices available while writing it.

Everything below is measured against *synthetic* banks: RS3-shaped panels drawn
by `tools/make_fixtures.py` with a bordered slot lattice, a
"The Bank of Gielinor" header, and stack counts in the game's yellow/white/green
bands with the same hard black outline. That is a fair test of the *structure* —
grid geometry, colour handling, ambiguity, valuation arithmetic — and a poor
test of the *font*, because the fixture text is DejaVu Sans Bold and RS3's is
not.

So: the geometry and identification numbers should transfer. The OCR number
should not be trusted until you re-measure it on your own screenshots.

## Phase 2 — bank detection and grid cropping

| Check | Result |
|---|---|
| Grid geometry vs ground truth | exact on cols, rows and cell size; origin within 1px |
| Survives 1.25x UI scaling | yes, cells detected at the scaled size |
| Empty slots skipped | 32/32 filled slots found, 8 empty slots correctly skipped |
| Bank correctly detected | yes, confidence 1.00 |
| 4-column inventory rejected | yes — refused as too narrow to be a bank |

The detector infers the lattice from the periodicity of the edge map rather
than from a calibrated window size, which is why the scaling case works. The
brief allowed requiring a fixed window size for the MVP; that turned out not to
be necessary.

## Phase 4 — icon identification

Measured over all 32 filled slots:

| Metric | Result |
|---|---|
| Correct item, rank 1 | **32/32** |
| Wrong item returned | 0 |
| Falsely flagged ambiguous | 0 |

Two things were needed to get there.

**Shape alone is not enough.** Matching with `TM_CCORR_NORMED` scored almost
everything above 0.99; the mean gap between the best and second-best candidate
was 0.03, so a sane ambiguity threshold flagged 14 of 32 slots as unsure even
though the top pick was always right. Switching to the mean-subtracted
`TM_CCOEFF_NORMED` raised that gap to 0.10, and blending in a masked hue /
saturation histogram (30% of the score) raised it to 0.18 and cleared every
false flag.

**The ambiguity flag earns its place.** The fixture set contains deliberately
near-identical pairs, standing in for the herbs the brief warns about. On those:

| Input | Top match | Runner-up | Verdict |
|---|---|---|---|
| `similar_herb_0a` | Similar herb 0a (0.758) | Similar herb 1a (0.758) | ambiguous |
| `similar_herb_0b` | Similar herb 1b (0.757) | Similar herb 0b (0.757) | ambiguous |

Note the second row: the top match is **wrong**. The flag caught it. That is the
case the whole design is for — a silently wrong item name changes the bank total
and nothing tells you.

## Phase 3 — stack-count OCR

This is the weak spot, and the brief predicted it would be.

| Reader | Accuracy on fixtures |
|---|---|
| Tesseract, best of 54 preprocessing configurations | 17/32 (53%) |
| Glyph template matching, rendered templates | 19/32 (59%) |
| **Both combined, with colour-band arbitration** | **21/32 (66%)** |
| — of which called high-confidence | 18/21 correct (**86% precision**) |

The brief's target is >95%. We are not there on synthetic text.

What was tried and rejected, with numbers, so nobody repeats it:

- **Tesseract preprocessing sweep** (3 upscales x 2 interpolations x 3 dilations
  x 3 page-segmentation modes): plateaued at 17/32. Tesseract wants prose; a
  two-character string from a 13-symbol alphabet at ten pixels tall is not that.
- **Connected-component segmentation**: the game's outline welds adjacent digits
  together — the `00` of `100` arrives as one blob — so cutting on components
  merges characters. Replaced with a width-weighted dynamic program that
  segments and recognises in one pass.
- **Forced-alignment template bootstrapping** (align known labels against the
  strip, average the aligned pieces into new templates, iterate): made things
  *worse*, 19/32 → 15/32 over three iterations. A bad segmentation averages bad
  pixels into the template and the error compounds. Not shipped.

One genuine bug was found and fixed along the way: stack-count colour was being
chosen by raw pixel count, so a **green item icon behind a yellow count won the
vote** and the resulting mask contained the icon instead of the digits. Scoring
colours by how many of their pixels sit against the text's black outline fixed
it — 29/32 → **32/32** on colour selection.

### Why the honest answer is calibration, not more tuning

Accuracy became very sensitive to the template render size (19% / 59% / 16% at
10 / 11 / 12px). That sensitivity is the tell: at that point the tuning is
fitting DejaVu Sans Bold, which is not the font RS3 draws. Pushing 66% to 95%
against the wrong font risks producing something that is *worse* on the right
one.

So the shipped position is:

1. The reader reports a confidence, and the pipeline **refuses to count a
   low-confidence quantity** (`min_quantity_confidence`, default 0.5). An
   uncertain slot appears in the overlay as unreadable instead of silently
   contributing a wrong number.
2. `tools/calibrate_digits.py` builds templates from **your** screenshots. It
   asks you to name ~13 glyph shapes, once, and writes
   `assets/font/stack_digits.json`, which the app then prefers over the
   rendered approximations.

Re-measure after calibrating. That is the number that decides whether this is
usable, and it is the one I could not produce from here.

## Phase 5 — valuation

Arithmetic, fully covered by tests: the total is exactly the sum of the slots
shown, slots that failed at any stage are excluded and listed separately, stale
cached prices are flagged, and a corrupt cache file does not stop startup.

The `29/32 slots valued` line in the overlay is deliberate. A total computed
from 29 of 32 slots is a different claim from a total computed from all 32, and
the UI should never let those look the same.
